# PSC-Eval · 问题空间构建评测器（C 组）

> **Problem-Space-Construction Evaluation** — 一把量「Agent 有没有构建问题空间」的尺子。
> 三组分工中，C 组负责**把这个总问题变成可判定的形式**。

---

## 这是什么

一个 Agent 在给定问题空间里做得好，和它**自己构建了问题空间**，是两件事。
后者没法用「宽度」「矛盾率」「多样性」这些指标直接测——因为**新方向天然没有 ground truth**。

PSC-Eval 解决这件事的方式：**不去问"这个方向对不对"，改问"这个方向有没有被生成 / 有没有被保留 / 有没有被呈现"**，
再用**词法基线**做对照，回答"抽取器是否真的学到了语义，还是只在做字串匹配"。

## ⚠️ 这把尺子测不了什么（必读）

**① 主指标测的是「规则执行一致性」，不是「发现能力」。**

金标是**人按同一套规则人工构造**的，抽取器也**按同一套规则**判 ——
高一致性部分是**同义反复**。
> **任何用「人按规则造金标 + 模型按同一规则判」方式做的评测，
> 其分数上界是「规则执行一致性」，而非能力本身。**

「发现失败」这一维在闭卷下**不可度量**（三面围堵：违反禁区 / 标注者主观 / 被候选集措辞遮蔽）。
**测「发现能力」要用 PRP 探针 + 前提依赖型任务。**

**② `expression_failure` 是定向构造的**，不是自然分布 —— 6 条均带 `constructed_for` 标注，
该类召回率**不得单独引用**。

**③ 跨组比较前必须核对三项同口径**：同一匹配阈值（当前钉在 0.25）、同一评分器、同一池口径。

## 七次「假通过」与六个自动防线

| # | 症状 | 失败方向 |
|---|---|---|
| ⑯-b | `fp` 逐条覆盖 | 报得比实际好 |
| ⑰-e | 旧 CSV 继承错值 | 污染下游 |
| ⑳-a | 池口径不一致 | 量的不是同一个东西 |
| ㉓-c | 分支永不进入 | 那段逻辑从未被执行 |
| ㉖-a | 循环论证的断言 | 参照物 = 被断言对象 |
| ㉘-b | 「抽取器过宽」（判断错误） | 实为规则与金标不一致 |
| ㉙-a | 「泄漏导致方向错乱」（判断错误） | 实为立场错判 |

**通则**：
> **① 汇总量只能定位「哪儿有差异」，不能定位「谁错了」——方向性归因必须逐条核。**
> **② 结论若依赖「分片间方向一致」，必须在全部分片上验证并给出逐分片的数。**
> **③ 不报错 ≠ 算对了。**

六个自动防线：**版本锁**（金标 md5 + prompt sha，评分前强制校验）·
**口径不变式**（assert 抛 `CaliberError`）· **反向断言**（每条门槛断言都配反向测试）·
**可达性断言**（枚举集合 ⊆ 实际可达分支）· **可核率硬闸门**（>0 即中止，禁止跑分）·
**只读清单**（执行体允许读哪 4 个文件 —— 防止裁决记录里的金标答案泄漏给执行体）

## 快速开始

```bash
# 评测器自检（363 项）
python3 eval/evaluator.py --self-test

# 渲染抽取器 prompt（带金标 md5 版本锁）
python3 run/render_prompts.py --round-tag "my-run" --manifest run/prompts_manifest.json

# 跑 M2（闭卷）
python3 eval/evaluator.py \
  --gold goldset/gold_v1.jsonl --pred <pred.jsonl> \
  --baseline-main-caliber eval/baseline_main_caliber.json \
  --sweep --sweep-step 0.05 --out report.json
```
