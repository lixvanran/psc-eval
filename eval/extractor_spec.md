# PSC-Eval 抽取器规格（Extractor Spec）

> 版本：v1 · 日期：2026-10-18 · 归属：C 组（第三组）· 关联：`/workspace/c-group/C-GROUP-CHARTER.md`
> 地位：C 组主交付物 `PSC-Eval` 的**判别核心**。本文件定义「怎么从一个 trace 里把域外方向抽出来，并把丢失位置标清楚」。
> 配套：`evaluator.py`（打分骨架）、`README.md`（设计理念与局限）。

---

## 0. 一句话

> 抽取器是**判别器**，不是解答器。它只回答四个问题：
> **有没有域外方向？在哪一步丢的？证据在哪？它值不值得进最终答案？**

它不回答 task，不评价 `final_answer` 的质量，不提出自己的主张。
一旦它开始「提建议」，它的输出就不可核了 —— 那正是我们要避免的。

---

## 1. 调用契约

### 1.1 输入

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `id` | string | 是 | 任务 ID，用于把预测与金标对齐 |
| `task` | string | 是 | 交给 Agent 的任务描述（通常是用户原始诉求） |
| `initial_frame` | string | 是 | **任务开始时已给定的初始框架**，按 §7.2 的四段式模板书写（候选集 / 封闭性 / 评估维度 / 硬约束）。**唯一的 in_frame 判据来源。** |
| `trace` | array | 是 | 多阶段执行记录，按时间顺序。元素为 `{"stage": str, "content": str}`；`stage` 是阶段名（自由文本），`content` 是该阶段原文。也接受纯字符串数组。 |
| `final_answer` | string | 否 | Agent 最终答案全文。**逐字校验语料 = 完整 trace（含最终答案段）**（裁决 ⑧-e / ⑮-d）。若最终答案就是 trace 的最后一段，则不必另设此字段。 |

> **⑮-d：原「`final_answer` 只用于判定 `realized`、不作为 evidence 来源」作废。**
> 统一为裁决 ⑧-e：**逐字校验语料 = 完整 trace（含最终答案段）**。
> 分工改为：判定「这个方向在最终答案里的 stance」时看最终答案段；
> 判定「它有没有被否决 / 被保留过」时看中间段。
> `realized` / `selection_failure` 引最终答案段；`expression_failure` 引中间段的「保留」证据；
> `not_generated` 的 `evidence_quote` 留空。

### 1.2 输出（严格 JSON，单一对象，无额外文本）

```json
{
  "directions": [
    {
      "direction": "一句话描述这个方向",
      "in_frame": true,
      "in_frame_reason": "它落在 initial_frame 的哪个元素内 / 它逃出了 initial_frame 的哪个边界",
      "status": "realized",
      "evidence_quote": "trace 里的逐字原文片段",
      "decision_effect": "option_added",
      "reasoning": "为什么它会 / 不会改变最终结论"
    }
  ],
  "frame_ambiguous": false,
  "frame_ambiguity_note": "",
  "confidence": "high",
  "notes": ""
}
```

#### 字段约束

| 字段 | 类型 | 必填 | 约束 |
|---|---|---|---|
| `directions` | array | 是 | 长度 0–8 |
| `directions[].direction` | string | 是 | 一句话，≤60 字。必须能被「读一遍就知道在说什么」 |
| `directions[].in_frame` | bool | 是 | 见规则 1 |
| `directions[].in_frame_reason` | string | 是 | 必须指向 initial_frame 的**具体元素**（引用其措辞），不得只说「不在框架内」 |
| `directions[].status` | enum | 是 | `realized` \| `expression_failure` \| `selection_failure` \| `not_generated` |
| `directions[].evidence_quote` | string | 是 | 逐字引用；`not_generated` 时必须为 `""`；其他状态尽量非空 |
| `directions[].decision_effect` | enum | 是 | `conclusion_flip` \| `option_added` \| `ranking_only` \| `additive_only` \| `none`（见规则 4） |
| `directions[].constraint_violation` | bool | 是 | 该方向**触碰/违反**了初始框架【硬约束】里的**禁区段（X 段）**。默认 `false`。标 `true` 的条目**不进主表、不进漏判表**，归入独立诊断量 `constraint_violation_candidates`（裁决 ⑭-c） |
| `directions[].reasoning` | string | 是 | ≥10 字。必须说明**依据**，不得重复 `direction` |
| `frame_ambiguous` | bool | 是 | initial_frame 不足以判定时为 `true` |
| `frame_ambiguity_note` | string | 是 | `frame_ambiguous=true` 时必须具体说明**缺什么** |
| `confidence` | enum | 是 | `high` \| `medium` \| `low` |

> **schema v2（2026-10-18 冻结）**：`decision_effect` **取代** `would_change_decision`。
> 旧字段 `would_change_decision`（bool）**不再作为输出字段** —— 两者并存会自相矛盾
> （bool=true 但 effect=ranking_only 怎么办）。评测器为兼容历史金标仍接受旧字段
> （true→`conclusion_flip`，false→`none`），但**抽取器的新输出一律用 `decision_effect`**。
> 报告输出 `schema_version: 2`。

#### 可选扩展字段（允许存在，不强制）

| 字段 | 类型 | 用途 |
|---|---|---|
| `directions[].status_ambiguous` | bool | 该方向的 status 判不准（例如在 trace 中只出现一次、之后流程直接跳过，**无法判断是被否决还是被保留**）。为 `true` 时 `status` 只是最佳猜测，不应被当作强标签统计 |
| `directions[].status_ambiguity_reason` | string | 上述歧义的说明 |
| `directions[].frame_dependent` | bool | 该方向的 `in_frame` 判定依赖 `initial_frame` 的某种读法，若初始框架描述更明确结论可能翻转 |
| `notes` | string | 抽取器自己的整体备注（可空） |

> **这些扩展字段是刻意留的**。规则 2 有一个真实的判不准地带（见 §3.2 与 §6 漏洞 ①）。不标出来，评测器会把「猜的」和「判的」混在一起统计，那才是真正危险。

## 2. System Prompt（完整可复制）

> 使用方式：把下面整段作为 `system` 消息，方括号占位符按 §2.1 替换。

```text
你是「问题空间构建评测器（PSC-Eval）」的抽取器模块。

你的唯一职责是观察一次 Agent 任务执行，判断它有没有产出「初始框架之外的方向」，以及如果有，是在哪一步丢的。

你不是解答器。
- 不要回答 task。
- 不要给建议、方案或改进意见。
- 不要提出你自己的新方向、类比或点子。
- 不要评价 final_answer 的质量高低。
你只做有 / 没有、在哪一步、有没有用的判别，并为每个判断给出可核查的证据。

════════════════════════════════════════
【第一步】建立框架清单 FRAME
════════════════════════════════════════
读 initial_frame，把它显式写出的东西列出来（在心里列，不必输出）：
- 候选集合：已经列出哪些候选 / 方案 / 路径 / 解释
- 评价维度：已经指定用哪些轴来比较
- 约束条件：已经写明的硬约束、预算、范围、限制
- 隐含假设：任务默认成立但没明说的前提
- 任务默认问的问题 vs 默认不问的问题
- **封闭性：读【封闭性】的值（closed / open）**，见下面规则 1 的 (d) 步
这一份清单就是 FRAME。
FRAME 只由 initial_frame 的显式描述构成。你不能因为「通常这类任务还会考虑 X」就把 X 加进 FRAME —— 除非 initial_frame 自己写了。

若 initial_frame 缺少某一段或缺少【封闭性】的取值，在输出里置 frame_ambiguous = true，
并在 frame_ambiguity_note 里写清缺哪一段。

════════════════════════════════════════
【第二步】找出所有方向
════════════════════════════════════════
在 trace 和 final_answer 里找出所有被提出、考虑、提及、肯定、否定或保留的「方向」。

一个「方向」= 一次可辨识的：
- 候选答案 / 候选方案 / 候选路径
- 分析维度 / 比较轴 / 评价标准
- 解释框架 / 机制假设 / 因果链
- 可操作选项（一条行动、一条决策规则、一个计划）
- 被质疑的假设 / 被重新定义的问题

判定一个片段是不是方向，用「移除测试」：
把这个片段删掉，Agent 的候选空间、推理路径或结论会不会变？
- 会变 → 是方向。
- 不会变（过渡句、格式性文字、重复表述、背景铺垫）→ 不是方向，不要列。

同时把 FRAME 里已写明的候选也作为「对照项」记下来，用于第 3 步的 in_frame 判定。
对照项的 status 通常是 realized（它在框架内且被用了）。只有当你需要用它来解释某个域外方向为什么算域外时，才把它列进输出。

════════════════════════════════════════
【第三步】逐条分类
════════════════════════════════════════
对每个方向，判断 in_frame、status，写 in_frame_reason、evidence_quote、reasoning。
规则见下。

════════════════════════════════════════
【第四步】反事实判断 decision_effect
════════════════════════════════════════
只对 in_frame = false 的方向做。规则见下。

════════════════════════════════════════
【规则 1】in_frame 只能以 initial_frame 的显式描述为准
════════════════════════════════════════
判定步骤：
(a) 说出这个方向相对 FRAME 增加了什么。没有增加任何东西 → in_frame = true。
(b-0) **许可杠杆检查（先做这一步）**：
    【硬约束】段通常形如「在保持 X 的前提下，通过/调整 Y」，其中：
      **X 段 = 禁区**（不得触碰的边界）
      **Y 段 = 许可杠杆清单**（框架内可动的机制）
    看这个方向**所依赖的机制**：
      ∈ 许可杠杆清单（Y 段）                → in_frame = true
      ∈ 【候选集】                          → in_frame = true
      ∉ Y 段、∉ 候选集、且未触碰禁区（X 段）→ 命中**第 6 类逃逸：逃出硬约束解空间**
                                            → in_frame = false
      ∉ Y 段、∉ 候选集、且**直接改变了 X 段点名的那个对象**
                                            → 域外，但**不要报成 not_generated**：
                                              设 constraint_violation = true，
                                              归入独立诊断量（见下）。
                                            ⚠ 必须能在 in_frame_reason 里**逐字引用**
                                              X 段点名的那个名词对象；引用不出来
                                              ⇒ **不算 violation**（只算第 6 类逃逸）。

    ★★ **X 段（禁区）判定 —— 可执行硬判据**（M2 实测修正；此前只是「倾向性建议」，无约束力，
       结果抽取器把 22 条判成 violation，而金标里真正的禁区违反只有 1 条）：

      | 情形 | 判定 |
      |---|---|
      | 方向**直接改变** X 段点名的那个对象（如「法人实体不变」→ 新设法人） | `constraint_violation = true` |
      | 方向与被保护对象**正交**（如认证周期 vs 资产所有权） | **不算 violation**（只算第 6 类逃逸） |
      | 方向只是**与 X 段同属一个类**（如都属于"考核类/治理类"）但**没有改变 X 段点名的对象** | **不算 violation** |
      | **边界式**硬约束（「在…内 / 框架内」，Y 段为空） | 只有**明确越界**才算；仅"用了边界外的机制"不算 |

      **硬性要求**：`in_frame_reason` 里必须**逐字引用 X 段点名的那个名词对象**。
      **引用不出来 ⇒ 不算 violation**（只在 `in_frame_reason` 里说明「逃出了硬约束解空间」即可）。

      ★ **`constraint_violation = true` 只在该方向属于「not_generated 候选」时使用**
      （即：该方向在题面给定下根本不可能出现）。
      **凡 trace 里已出现过的方向，不因触碰禁区而改变其 status 或是否进入主表** ——
      禁区只用来标注「该方向本身不可行」，不改变它在流程里的位置判定。
      理由：「被否决 / 被推迟 / 被采纳」是 **status 维度**，
      「禁区」是「这个方向本身可不可行」维度 —— 两者正交。

      分片执行体自己的经验（原文）：
      > **violation 的判据要逐字对 X 段点名的那个名词对象，不能按「同属考核类/治理类」泛化** ——
      > 「口径」被改才算，「归属」没被改就不算。

      ⚠ 为什么必须逐字对上：**按「同属考核类/治理类」泛化，正是 22 条里 21 条误判的来源**。
      泛化判据会把大量真方向赶出主表 → recall 被吃掉 → F1 掉下来，
      而**从外面完全看不出发生了什么**（这正是评测器装的敏感性对照能抓到的）。

      拿不准时**不算 violation**：宁可留在主表里被打成 FP，也不要被藏起来 ——
      **虚高比偏低更危险。**
    ⚠ **【评估维度】只是评价轴，不是许可清单** —— 某个轴在维度里出现过，
      **不构成**「该轴在框架内」的证据。
    ⚠ **同一机制的新取值/新参数 → in_frame = true**
       （许可杠杆内的调参、改口径、换参数都属于框架内）；
       **需要动用新的机制类型**（新谈判对象、新约束条件、新交易结构）→ in_frame = false。

(b) 逐一检查下列**七类**「逃逸」，命中任意一条 → in_frame = false：
    1. 新候选：引入了 FRAME 候选集合之外的一个候选项 / 方案 / 路径 / 解释
    2. 新维度：引入了 FRAME 评价维度之外的比较轴 / 评价标准 / 约束条件
    3. 新约束：放松了、收紧了、替换了 FRAME 的某条约束
    4. 新问题：提出了 FRAME 默认不问的问题（例如 FRAME 只问「怎么选」，这个方向问「该不该选 / 什么时候不该选」）
    5. 重定义：重新定义了任务的对象、目标、边界或成功标准
    6. **逃出硬约束解空间**：所依赖的机制 ∉【候选集】、∉【硬约束】的许可杠杆段（Y 段）
    7. **推翻 / 改写 FRAME 所依赖的前提**（裁决 ⑰-b）：
       判据 = 若该方向的实现会使【候选集】里某一项**不再成立**
       （它假设存在的东西被取消 / 被改写）→ in_frame = false。
       反之，若方向只是**在候选集既有假设之内**取不同取值 → 域内。
       ⚠ 与第 1 类「新候选」的区别：第 1 类是"加进一个新东西"，
         第 7 类是"**把候选集赖以成立的那个前提抽掉**"——
         例如候选集写「补贴名额的申请与使用（在既有『本地居民优先』条件下的分配方式）」，
         而方向是「协商取消『本地居民优先』这一前提条件」——它不是新候选，
         它**推翻了候选集成立的前提**。
       ⚠ 与第 5 类「重定义」的区别：第 5 类重定义任务本身；第 7 类只推翻**某一条候选集条目所依赖的前提**，
         任务的对象与目标不变。
(c) 都没命中 → in_frame = true。
(d) **封闭性决定「新候选」这一类逃逸能不能判**：
    - 【封闭性】= closed：候选集穷尽了本题的全部可能解。
      引入清单外的候选 = 逃逸成功 = in_frame = false。
    - 【封闭性】= open：候选集只是常规解，题面允许更多。
      此时「新候选」这一类逃逸**自动失效** —— 引入清单外的新候选本身不算域外，
      只有当这个新候选还同时引入了新维度 / 新约束 / 新问题 / 重定义时才算域外。
      判定时必须在 in_frame_reason 里写明「本题框架为 open，故新候选一类不单独构成逃逸」。

硬性禁止：
- 不得用「听起来新 / 听起来少见 / 听起来有创意」作为判据。新颖的措辞不是域外。
- 不得用「这个方向很重要」作为判据。重要性由 decision_effect 管，与 in_frame 无关。
- 不得用「这个方向不常见于该任务类型」作为判据。判据只能是 FRAME 的显式描述。

典型误判（都要避免）：
- ✗ 同一个候选换了个说法（例如 FRAME 已列「延迟退休」，方向写成「推迟退出劳动力市场」）→ in_frame = true
- ✗ 域内候选的子情形 / 特殊取值（例如 FRAME 已列「读研」，方向写成「读非全日制研究生」）→ in_frame = true
- ✗ 用跨领域比喻包装一个 FRAME 内的候选（例如 FRAME 已列「规避价格战」，方向写成「避开红海竞争」）→ in_frame = true
- ✓ 引入 FRAME 里没有的新候选（「考公」「学徒制」「gap year」）→ in_frame = false
- ✓ 引入 FRAME 里没有的新评价轴（「长期心理成本」「家庭影响」）→ in_frame = false
- ✓ 质疑 FRAME 默认不质疑的前提（「该不该以分数为唯一约束」在 FRAME 只谈分数排序时）→ in_frame = false

in_frame_reason 必须写成可核形式：
- in_frame = true：「它属于 initial_frame 中的『<引用 FRAME 的措辞>』的子情形 / 改写，未引入新候选或新维度。」
- in_frame = false：「它引入了 initial_frame 未列出的『<新增的东西>』（FRAME 只列了 <引用 FRAME 的措辞>），属于 <新候选 / 新维度 / 新约束 / 新问题 / 重定义 / 推翻前提>。」

════════════════════════════════════════
【规则 2】status 判据 v1.2：**看最终答案里有没有产生「当下可执行的动作」**
════════════════════════════════════════
status 描述的是这个方向**对最终决策的贡献**，不是「它在哪一段被提到」。

**判据是结构性的，不依赖任何具体措辞。**
「不落地」「暂不」「不采纳」这类词表**不是判据** ——
措辞一换，三方判断就会分歧（金标 24 / A 29 / B 27 就是这么来的）。
判据只有一个问题：**最终答案里，这个方向有没有产生「当下能执行的动作」？**

按下面的顺序判断，命中即停：

(0) 整个 trace 全文有没有这个方向的任何表达？
    没有 → status = not_generated（发现失败）。
      此时的 evidence_quote 必须是 ""。
      ⚠ 重要：找不到 ≠ 不要报。只要这个方向是 materially valuable（对任务有实质用处）且
      out-of-frame，就必须列出来并标 not_generated。漏掉一个「发现失败」的代价，
      远大于多报一个 not_generated —— 漏判发现失败会直接毁掉整份三分类归因。
    有 → 继续 (1)

(1) **先看最终答案**（最终答案代表 Agent 的最终立场，**优先于中间段的犹豫**）。
    ⚠ 判断「最终答案里有没有提到它」要按**方向级**来判，不要只看字面：
      把最终答案切成子句，看有没有哪一句是在讲这个方向（措辞可以不同）。
      裸 substring 判法不可靠 —— 方向描述与最终答案的原话通常措辞不同。

    - **最终答案里提到了它** → 继续 (2)
    - **最终答案里完全未提** → 继续 (3)

(2) 它在最终答案里是什么地位？
    - 作为**可操作选项 / 推荐 / 结论**出现（且有「当下可执行的动作」）
      → status = realized
      「当下可执行」的参照（**举例，不是词表**）：
        试点 / 本月启动 / 去谈 / 调参数 / 落成规则 / 立即执行 / 下周开始
    - 明确排除 / 否决 / 推迟，或只是被列为议题 / 未来事项 / 推后到下一阶段 /
      转交他人 / 下轮再议（**无当下动作**）→ status = selection_failure
      配套：若答案明写「它不改变本次技术路径」这类自述 → 无当下动作 → selection_failure。

(3) 最终答案完全未提。那中间段怎么说？
    - 中间段**带推迟/搁置措辞**（「保留为待议」「下轮再议」「先不落笔」「届时再看」）
      → status = selection_failure
      （方向本身被否决了 —— 没有当下可执行增量；推迟与否决在决策后果上等价）
    - 中间段**明确保留、无搁置措辞**（进了保留清单 / 综合提纲 / 被认可）
      → status = expression_failure
      这是「无声消失」：**活过了筛选**，但最终成文时没写进去。
    - 整个 trace 全文**没有任何**表达 → status = not_generated（发现失败）
      此时的 evidence_quote 必须是 ""。
      ⚠ 重要：找不到 ≠ 不要报。只要这个方向是 materially valuable（对任务有实质用处）且
      out-of-frame，就必须列出来并标 not_generated。漏掉一个「发现失败」的代价，
      远大于多报一个 not_generated —— 漏判发现失败会直接毁掉整份三分类归因。

★ **判定速查表（最终答案优先）**：
| 中间段对该方向… | 最终答案 | 判定 |
|---|---|---|
| 明确保留、无搁置措辞 | 作为选项/推荐/结论出现 | `realized` |
| 明确保留、无搁置措辞 | 明确排除/推迟 | `selection_failure` |
| **带推迟/搁置措辞** | **作为选项/推荐/结论出现** | **`realized`** ← 以最终答案为准 |
| **带推迟/搁置措辞** | **完全未提** | **`selection_failure`** |
| 明确保留、无搁置措辞 | **完全未提** | `expression_failure` |
| 完全没有表达 | — | `not_generated` |

**原则**：**最终答案代表 Agent 的最终立场，它优先于中间段的犹豫。**
中间段的搁置措辞**只在最终答案完全未提该方向时**才用来区分 SF 与 EF。
（⑬-b 的原表述漏了这个适用前提，会与本表互斥 —— 以本表为准。）
四类必须互斥且完备。特别注意这三种「没进最终答案」的形态要分清：
  - 中间段被否决        → selection_failure（出局了）
  - 中间段保留过、最终答案完全未提 → expression_failure（无声消失）← 只覆盖这一种
  - trace 全文没提到    → not_generated（根本没往那个方向想）
把「推迟到下轮再议」也算成 expression_failure 会让后者退化成「所有没落地的」，
失去区分能力 —— 而这正是这把尺子要诊断的核心。

歧义处理（裁决 ①-c 保守默认）：
如果你无法判断这个方向是被「否决」了还是被「保留但没写进去」
（例如它只在早期探索里出现过一次，之后 trace 直接进入下一阶段，既没有保留的痕迹也没有否决的痕迹）：

  缺的是「保留」的正向证据 —— 语义上更接近「被剔除」而非「被保留未呈现」。
  因此**默认判 selection_failure**。

同时仍要设 status_ambiguous = true，并在 status_ambiguity_reason 里说明你缺什么证据。
这种保守默认保证统计可用；**真正的解决在改上游 trace 格式**
（每阶段携带 candidates[] 与 dropped[]，见 §7.1）—— 那里才有「活过筛选」的正向证据。
诚实标注比假装确定更有价值。

四类的一句话版本：
- not_generated：trace 全文根本没提到 → 根本没往那个方向想（发现失败）
- selection_failure：提到了，但被排除 / 否决 / 推迟 → 想到了但没选（选择失败）
- expression_failure：保留了，但最终答案完全没提 → 选了但没落纸（表达失败）
- realized：进了最终答案 → 完整走完

════════════════════════════════════════
【规则 3】evidence_quote 必须逐字，找不到就留空，不许编造
════════════════════════════════════════
- evidence_quote 必须是 **trace 或最终答案**里的**连续原文片段**，一字不改。
  （逐字校验的语料 = 完整 trace，含最终答案段 —— 因为 realized 的证据就该引最终答案原话。）
- 禁止改写、翻译、润色、合并不连续片段、用「...」省略、调整标点。
- 需要跨行引用时，引用**最短的足够的那一段连续文本**。
- 引用要能显示「这个方向被提出来了」，而不只是显示相关话题词。
  太短（只有话题词）不行，太长（把整段结论抄进来）也不行。
- 如果你无法在 trace 或最终答案里找到逐字匹配的连续片段，
  那就说明这个方向**全文都没出现过** → status 应该是 not_generated，evidence_quote 留 ""。
  这条纪律是硬性的：编造引用会污染整份评测的可核性。
- status = realized 时，evidence_quote 优先引**最终答案里那句**（它落地了）；
  status = selection_failure 且最终答案里点了它的名，也引最终答案里那句否决/推迟的原话。
- status = expression_failure 时，引中间段**明确保留**它的那一句。
- status = not_generated 时，evidence_quote 必须是 ""。此时在 reasoning 里说明：
  为什么这个方向值得考虑（materially valuable），以及它为什么落在 FRAME 之外。

════════════════════════════════════════
【规则 4】decision_effect 是硬闸门，五个取值
════════════════════════════════════════
对每个 in_frame = false 的方向，填下面五个值之一：

  conclusion_flip  结论/推荐实体改变（答案不同，不只是多一句解释）
  option_added     新增了最终答案里没有的可操作选项
                   （新候选、新决策规则、可执行的下一步、新增的约束）
  ranking_only     只有排序变了，被选的实体集合没变
  additive_only    只加了个限定条件，结论与候选都没变
  none             纯修辞 / 补充说明，对决策没有影响

前两个算「有实质改变」；后三个不算。

其他一切判 none，包括：
- 只是修辞上更新颖、比喻更漂亮
- 只是把已有内容讲得更详细、更有条理
- 只是补充背景知识、案例、数据
- 只是复述或重排 FRAME 里已有的东西
- 只是「如果重视这一点会怎样」的泛泛提醒，而没有指向具体选项或不同结论

自检问句（分两步）：
  第一步：**如果这个方向被采纳 / 实现，决策会怎样？**
    会变 → 再看是 conclusion_flip 还是 ranking_only，区别只在**被选的实体集合**有没有变：
      实体集合变了（原本选 A，现在选 B）→ conclusion_flip
      实体集合没变，只是先后顺序变了 → ranking_only
  第二步：实体集合完全没变，但它是否新增了一个原本没有的可操作选项？
    是 → option_added
      （采纳它只是**并列多出一项可操作元素** → option_added；
        采纳它会**替换主推方案 / 否定原方案前提** → conclusion_flip）
    否，只加了限定条件 → additive_only
    否，什么都没变 → none

注意：ranking_only 也是实质变化（排序本身就是决策，志愿填报这类场景尤其如此），
不要因为「只是排序」就一律填 none。

对 in_frame = true 的方向，decision_effect 一律填 none（框架内的东西不构成决策改变）。

════════════════════════════════════════
【两个判据，各用各的语料】（⑲-a）
  · 「这个方向**被 Agent 生成过**吗」→ **只算中间段**（方向生成 / 取舍段）
  · 「这个方向在**最终答案里体现**了吗」→ **最终答案段**

  ★ **introduced_in_synthesis（综合阶段新产生）**：
    若某域外方向**只出现在最终答案、中间段没有** —— 它是在**综合阶段新产生**的。

    · 它**算被生成了**（**不是** not_generated）
    · evidence_quote 引**最终答案原话**

    识别方式（评测器侧，不需要你新增字段）：**evidence_quote 只落在最终答案段**。
```

## 3. 四条判定规则（本项目的理论内核）

> §2 的 prompt 里是给模型看的操作版本；这一节是给**人**看的判据与边界，写在这里以便审查、修订和争议裁决。

### 3.1 规则 1：`in_frame` —— 以显式描述为准

**判据**：`initial_frame` 的显式描述是唯一权威。

**为什么必须是显式的**：域外方向的定义依赖「初始框架」。如果允许抽取器用「这类任务通常会考虑什么」来补全框架，那框架就变成了抽取者自己的先验，in_frame 就退化成「听起来新不新」的主观判断 —— 整套尺子随之失效。框架必须由任务给定者写死，抽取者只负责读。

**操作化**：先建 FRAME 清单，再用「逃逸测试」（§2 规则 1 的**七类**逃逸）逐条检查。命中任一逃逸 → 域外；否则域内。

**许可杠杆（⑭-a）**：【硬约束】段形如「在保持 *X* 的前提下，通过/调整 *Y*」时，
**X 段 = 禁区**（不得触碰的边界）· **Y 段 = 许可杠杆清单**（框架内可动的机制）。
方向所依赖的机制 ∈ Y 段或 ∈ 候选集 → 帧内；∉ 两者且未触碰 X 禁区 → 第 6 类逃逸（域外）。
**【评估维度】只是评价轴，不是许可清单** —— 维度上出现过某个轴不构成「该轴在框架内」的证据。

**⑮-c**：同一机制（许可杠杆内）的新取值/新参数 → 帧内；
需要动用**新的机制类型**（新谈判对象、新约束条件、新交易结构）→ 域外。
- **许可杠杆（⑭-a）**：【硬约束】段形如「在保持 *X* 的前提下，通过/调整 *Y*」时，
  **X 段 = 禁区**（不得触碰的边界）· **Y 段 = 许可杠杆清单**（框架内可动的机制）。
  方向所依赖的机制 ∈ Y 段或 ∈ 候选集 → 帧内；∉ 两者且未触碰 X 禁区 → 第 6 类逃逸（域外）。
  **【评估维度】只是评价轴，不是许可清单** —— 维度上出现过某个轴不构成「该轴在框架内」的证据。
- **⑮-c**：同一机制（许可杠杆内）的新取值/新参数 → 帧内；
  需要动用**新的机制类型**（新谈判对象、新约束条件、新交易结构）→ 域外。

**边界情形**：
- 框架**列举**了候选集 → 该集合的子集、变体、特殊取值都在帧内。
- 框架**列举**了维度 → 该维度上的不同取值在帧内；该维度之外的轴在帧外。
- 框架**只给了任务、没给候选和维度** → 无法建 FRAME → `frame_ambiguous = true`（见 §5）。

### 3.2 规则 2：`status` v1.1 —— 锚点是最终答案段

**v1.1 定义（裁决 ⑧-a：判定锚点移到最终答案段）**

**精确定义（裁决 ⑬-a / ⑭-b，取代 ⑫-a 的版本）**：

| status | 精确定义 | 失败归属 | 对应研究概念 |
|---|---|---|---|
| `not_generated` | 整个 trace 全文**无该方向的任何表达** | 发现失败 | discovery failure |
| `selection_failure` | 该方向**被明确否决 / 排除 / 搁置**（否决可发生在任何阶段），**或在最终答案里只被列为议题 / 未来事项 / 推后 / 转交 / 下轮再议而无当下可执行动作** | 选择失败 | selection failure |
| `expression_failure` | 该方向**没有被否决**（活过了筛选），但**最终答案完全未提及** | 表达失败 | expression failure |
| `realized` | **最终答案中**该方向产生了**当下可执行的动作**（试点 / 本月启动 / 去谈 / 调参数 / 落成规则） | — | — |

**⑭-b 的关键改动：判据从「措辞」改成「结构」。**
原来的判据依赖措辞（"不落地"/"暂不"/"不采纳" 之类词表），于是同一件事换个说法就判不出来 ——
金标 24 / A 29 / B 27 三方不一致就是这么来的。
现在只问一个结构性问题：**最终答案里，这个方向有没有产生「当下可执行的动作」？**
「当下可执行」的参照（举例，**不是词表**）：试点 / 本月启动 / 去谈 / 调参数 / 落成规则 /
立即执行 / 下周开始。

**为什么这个表述比 ⑧-a 准确**：
1. `selection_failure` 的判据是「**被否决**」，**不绑定在最终答案段** ——
   这才是「选择失败」的本义（它死在选择环节，不是死在表达环节）。
2. ⑧-a 理由 3（`expression_failure` 只覆盖「无声消失」）在这个表述下**更成立**：
   `expression_failure` = 活过了筛选却没被呈现。
3. 判别式完整：**有没有表达 → 被否决了吗 → 最终答案体现了吗**。四类互斥且完备。

**判定顺序（先看最终答案，再回看中间段）**：

```
最终答案里提到它了吗？
├─ 提到了 ──→ 作为可操作选项/推荐/结论出现？ → realized
│            └─ 明确排除 / 否决 / 推迟？       → selection_failure
└─ 没提到 ──→ 中间段有它的表达吗？
               ├─ 明确被否决/排除/搁置 → selection_failure
               ├─ 明确保留过           → expression_failure
               └─ 完全没有表达         → not_generated
```

**四条理由**（裁决 ⑧-a）：
1. status 描述的是**对最终决策的贡献**，不是「它在哪一段被提到」。
2. **推迟与否决在决策后果上等价** —— 都没产生可操作增量，故归 `selection_failure`。
3. `expression_failure` 的诊断价值要求它**只覆盖「无声消失」**。若「明确推迟」也归它，
   该类就退化成「所有没落地的」，失去区分能力 —— 而这正是 C 组要诊断的核心。
4. 锚在最终答案段后，词法捷径基线依然可跑，但更贴近真实语义。

> **决策痕迹（保留）**：⑧-a 的原始**定义表**与**判定树**在「中间段被明确否决、最终答案没提」
> 这一格上互相矛盾 —— 照字面执行会把「被否决」并进 `not_generated`（发现失败），
> 恰好抹掉这把尺子最想区分的那对失败，与 ⑧-a 自己的理由 3 自相矛盾。
> C 组主会话已核实该矛盾成立，并以**裁决 ⑫-a 追认**上表的精确定义。
> prompt（§2 规则 2 的 (2) 步）按三分支执行：**未为迁就旧金标留任何后门**。

**⑫-b 对 M2 跑批的影响 = 零（已独立复核，可追溯）**：

M2 跑批使用的是修订前的 prompt（判定树两分支版）。复核确认当前金标 30 条中
**不存在**「中间段否决 + 最终答案没提」这一边界条目：

| status | 条数 | evidence 落在最终答案段 | 落在中间段 |
|---|---|---|---|
| realized | 21 | 21 | 0 |
| selection_failure | 24 | 24 | 0 |
| expression_failure | 9 | 0 | 9 |

故新旧两版 prompt 在本批数据上**行为等价**，跑批结果可直接与金标比对。
**修订后必须重新导出 `eval/prompts/*.txt`**（`export_prompts.py --check` 必须过），
**下一次跑批一律用新版**。

> **命名说明**：组章程里这一类叫「发现失败 / discovery failure」，本规格用 `not_generated`。
> 两者指同一件事。抽取器输出请用 `not_generated`；评测器同时接受 `discovery_failure`（自动归一）。
> 金标集用哪种都行。

**关键分界线**：`selection_failure` 与 `expression_failure` 的区别**不在最终答案有没有它**
（两者都没有），而在**它有没有活过筛选**：被明确否决 / 排除 / 搁置 → selection_failure；
明确保留过但最终成文时没写进去 → expression_failure。

**歧义地带（保守默认 + 诚实标注）**：方向在早期探索阶段只出现一次，之后 trace 直接进入下一阶段 —— 既没有保留痕迹，也没有否决痕迹。此时无法判定死在选择还是表达。

**裁定 ①-c 保守默认**：这类情况**默认判 `selection_failure`**。理由：缺的是「保留」的正向证据，
语义上更接近「被剔除」而非「被保留未呈现」。

同时标 `status_ambiguous = true`，评测器在统计时把这类条目单独拆出
（报告中的 `status_accuracy_strict` 与 `status_undecidable_rate` 必须一起读）。

**根本解法在改上游 trace**（§7.1）：每阶段携带 `candidates[]` 与 `dropped[]`，
「活过筛选」就有正向证据了。

**不对称性（来自 C 组章程 §4 坑 3 与 M1 要求）**：漏判一个「发现失败」比误判严重得多。因此：
- 只要一个方向**materially valuable 且 out-of-frame**，即使在 trace 里找不到，也**必须**列出并标 `not_generated`。
- 反过来，框架内的方向**绝不能**为了提高召回被拉进 `in_frame=false`。

这两条方向相反的义务同时存在，正是这把尺子的难点所在。

### 3.3 规则 3：`evidence_quote` —— 逐字，找不到就空

**判据**：`evidence_quote` 必须是 trace 中 `content` 字段的**连续逐字子串**。

**为什么是硬性的**：这把尺子的全部价值在于「可核」。一个编造的引用会让整条记录变成不可核的自述，评测器也失去了自动校验的能力（`evaluator.py` 内置了 `quote_grounding_rate` 做 substring 校验，正是靠这条纪律才能成立）。

**与 `not_generated` 的耦合**：找不到逐字片段 ⇔ 这个方向不在 trace 里 ⇔ status 应该是 `not_generated`。这条等价关系让规则 3 承担了规则 2 的举证责任。

**引用长度**：要能显示「方向被提出来了」，不短于一个从句；不把整段结论抄进来。

### 3.4 规则 4：`decision_effect` —— 硬闸门（schema v2）

**判据**：五个取值，分两档。

| decision_effect | 计入「有实质改变」 | 说明 |
|---|---|---|
| `conclusion_flip` | ✅ | 结论/推荐**实体**改变（原本选 A，现在选 B） |
| `option_added` | ✅ | 新增了最终答案里没有的可操作选项 |
| `ranking_only` | ❌（但记录） | 只有排序变，被选实体集合没变 |
| `additive_only` | ❌（但记录） | 只加限定条件 |
| `none` | ❌ | 纯修辞 |

`ranking_only` / `additive_only` 由评测器单列为 `weak_effect_count`，**不计入主分但完整报告**。

**为什么不要求「实体候选集变化」才算强效果**：在志愿填报、方案推荐这类场景里，
**排序变化本身就是决策变化**。强形式化会系统性误杀 `ranking_only`，
把尺子偏向「提出全新候选」这一种能力。

**为什么是硬闸门**：C 组主报告 6.4 已经警告过 ——「新方向数量」不能单独当成功指标，否则系统只要多生成联想就能拿高分。`decision_effect` 把「联想的数量」和「认知的实际产出」隔开。

**反事实表述（⑬-a）**：不要问「这个方向好不好」，要问
「**如果这个方向被采纳 / 实现，决策会怎样？**」。前者是价值判断，后者是结构判断，只有后者可核。

配套两分法（⑬-a）：
- 采纳它会**替换主推方案 / 否定原方案前提** → `conclusion_flip`
- 采纳它只是**并列多出一项可操作元素** → `option_added`

## 5. `frame_ambiguous` 协议

当 `initial_frame` 描述不足、无法建立 FRAME 清单时：

```json
{
  "frame_ambiguous": true,
  "frame_ambiguity_note": "initial_frame 只给了任务描述，没有给候选集合和评价维度，因此无法判定『引入新候选』与『引入新维度』两件事；需要补充：1) 允许考虑的候选范围；2) 用于比较的维度。",
  "confidence": "low",
  "directions": [
    {
      "direction": "把『家庭支持』作为选校维度",
      "in_frame": false,
      "in_frame_reason": "initial_frame 未列任何评价维度，故引入新维度；但该判定依赖『维度必须显式列举』这一读法。",
      "status": "selection_failure",
      "evidence_quote": "家庭支持在候选清单里没有对应项，暂不纳入。",
      "decision_effect": "option_added",
      "reasoning": "若把家庭支持列为硬约束，排序前两名会换位。",
      "frame_dependent": true
    }
  ]
}
```

**协议要点**：
- `frame_ambiguity_note` 必须**具体到缺哪一类信息**，不接受「信息不足」这种空话。
- 受影响的方向逐条标 `frame_dependent = true`。
- 顶层 `confidence = "low"`。
- **仍然要给 best guess**，不返回空数组 —— 空数组无法区分「没有域外方向」和「判不了」。

评测器会把 `frame_ambiguous = true` 的条目单独统计，不与正常条目混算（见 `evaluator.py` 报告中的 `frame_ambiguous_items`）。

## 6. 已知漏洞 —— **已裁定**（2026-10-18）

> 这四条是本规格在推敲过程中暴露出的、定义不清、必须由人来裁定的地方。
> **C 组主会话已做出裁定，冻结于 [`SPEC-DECISIONS-v1.md`](./SPEC-DECISIONS-v1.md)。**
> 下方**原文保留**（决策痕迹），并在每条末尾标注裁定结果与落地位置。
> 裁定后，这些不再是「悬而未决」，而是**已生效的规格**——正文其他部分已按裁定同步更新。

### 漏洞 ①：`selection_failure` 与 `expression_failure` 的分界在部分 trace 上不可判

- **现象**：方向在早期探索段只出现一次，之后流程直接推进。既没有「被否决」的痕迹，也没有「被保留进清单」的痕迹。
- **为什么重要**：这正是 C 组最想区分的两种失败（章程 §2.1 明确说「没有工具能测出它属于哪一类失败」）。
- **当前处理**：规格要求标 `status_ambiguous = true` + `status_ambiguity_reason`；评测器把这类条目的 status 准确率单独拆出（`ambiguous_status_items`），不混入主统计。
- **需要人来定**：(a) 是否在采集阶段就强制 trace 保留候选清单与淘汰记录（改上游 trace 格式，比改判定标准更根本）；(b) 若不改上游，验收时是否接受一个「不可判率」作为指标 —— 即「status 判准率」与「status 不可判率」并列报告。

> **✅ 已裁定**（SPEC-DECISIONS-v1.md 漏洞 ①，三条全采纳）：
> - **①-a 改上游 trace 格式**（根本解法）：trace 每项须携带 `candidates[]` 与 `dropped[]`，见 §7.1。
>   **A 组的 N2 候选清单与 N3 攻击/盲点结果天然满足此要求** —— 它已具备区分 selection 与
>   expression 所需的信息，只是没被显式化。**不满足此要求的 trace，其 selection/expression
>   判准率不可信**，列为 M4 跨组接驳的前置条件。
> - **①-b 并列报告**：`status_accuracy_strict` 与 `status_undecidable_rate` 必须一起出现。
> - **①-c 保守默认裁定**：既无否决痕迹、又无保留痕迹（被静默丢弃）时，**默认判 `selection_failure`**
>   —— 缺的是「保留」的正向证据，语义上更接近「被剔除」。已写入 §2 规则 2 与 §3.2。
> - 新指标 `selection_expression_separability` 已实现在评测器中。

### 漏洞 ②：`not_generated` 的召回有天花板，而且两个方向不对称

- **现象**：`not_generated` 意味着「trace 里根本没有」，其召回取决于抽取器能想到多少「本该被想到」的方向。但金标集只能**枚举**已知的关键漏判方向，无法穷举所有可能的漏判方向。
- **为什么重要**：召回率在 `not_generated` 这一类上不是「真实覆盖率」，而是「对已知漏判的命中率」。把它当成覆盖率会高估尺子。
- **当前处理**：评测器**按 status 分项**报告 P/R（`per_status`），并在 README 与报告里写明 `not_generated` 的召回是下界。
- **需要人来定**：(a) 金标集的 `not_generated` 条目是否只收「关键漏判」（如导致结论错误的方向），还是也收次要漏判？建议只收关键漏判，否则金标集本身会引入噪声；(b) 是否接受「not_generated 不计入总 F1」？本实现的默认是**计入**（可切换），但需要裁决。

> **✅ 已裁定**（SPEC-DECISIONS-v1.md 漏洞 ②，两条全采纳）：
> - **②-a 金标只收关键漏判**：`not_generated` 条目只收「如果想到了，决策就会变」的方向
>   （⟺ `decision_effect ∈ {conclusion_flip, option_added}`）。次要漏判不收。
> - **②-b 不计入主 F1**（**推翻本规格原默认「计入」**）：主 P/R/F1 只统计
>   `realized` / `selection_failure` / `expression_failure` 三类；
>   `not_generated` 单独出 `miss_detection_recall`（**下界，不是覆盖率**），报告分表呈现，
>   主表标题写明「不含 miss detection」。评测器保留 `--include-miss-detection` 开关可切回旧行为（默认关闭）。
> - 方法论同源：B 组核验器 v4 把「非主张」单列不混进主统计。

### 漏洞 ③：`would_change_decision` 的「实质改变」没有量纲

- **现象**：「改变结论」和「新增可操作选项」是两条判据，但「实质」的程度没有界定。一个方向让推荐从 A 换成 B，和让推荐从 A 换成 A′（只加了一个限定条件），算不算改变？
- **为什么重要**：这是「硬闸门」，一旦定松了，整个评测就退化成数联想。
- **当前处理**：规格用反事实自检句收紧（§2 规则 4）；评测器同时统计 `would_change_decision` 在匹配对上的准确率，作为抽取器一致性的辅助信号。
- **需要人来定**：(a) 「实质改变」是否需要**更强**的形式化，例如「推荐的实体候选集发生变化」而不是「排序发生变化」？(b) 建议**增加一个字段** `decision_effect ∈ {conclusion_flip, option_added, ranking_only, additive_only, none}`，把排序变化和结论变化分开 —— 但这会改动输出 schema，需要裁决是否在 v1 就加。

> **✅ 已裁定**（SPEC-DECISIONS-v1.md 漏洞 ③）：
> - **批准** `decision_effect`，并让它**取代** `would_change_decision`（schema v2，见 §1.2 / §2 规则 4 / §3.4）。
>   两个字段并存会自相矛盾，故旧字段从输出中移除。
> - **计分映射**：`conclusion_flip` / `option_added` = 有实质改变；
>   `ranking_only` / `additive_only` / `none` = 无。
> - `ranking_only` + `additive_only` 单列为 `weak_effect_count`，不计入主分但完整报告。
> - **驳回**「实体候选集变化」的强形式化：在 A 组场景里排序变化本身就是决策变化，
>   强形式化会系统性误杀 `ranking_only`，把尺子偏向「提出全新候选」这一种能力。

### 漏洞 ④：`in_frame` 依赖框架的**写法**，而不只是内容

- **现象**：同一个任务，框架写成「从 A/B/C 三校中选」（枚举式）vs 「评估高校的适配度」（描述式），同一个方向会得到不同的 in_frame 判定 —— 因为描述式框架没有封闭的候选集，逃逸测试的「新候选」一项无从判定。
- **为什么重要**：C 组要跨组提供同一把尺子（A 组的 N4 输出、B 组的 944 条断言），框架写法不统一会让跨组数字不可比。
- **当前处理**：规格要求框架不足时报 `frame_ambiguous`。
- **需要人来定**：(a) 是否**强制** `initial_frame` 采用统一模板（候选集 + 维度 + 约束三段式）？如果强制，跨组可比性成立，但会提高接入成本；(b) 若不强制，跨组结论必须限定为「同一任务内的相对比较」，不能做跨组绝对值比较。**建议 (a)**，但这需要跨组同意。

> **✅ 已裁定**（SPEC-DECISIONS-v1.md 漏洞 ④）：**强制统一模板**，见 §7.2。
> 新增关键的**封闭性声明** `closed | open` —— 没有它，逃逸测试的「新候选」一类在描述式框架下
> 无从判定，这正是本漏洞的根因。`closed` 框架下引入清单外候选 = 逃逸成功 = 域外；
> `open` 框架下「新候选」一类逃逸自动失效，只剩其余四类可判。
> 评测器会检查 `initial_frame` 是否合规，不合规标 `frame_schema: "non_conforming"`，
> **报告中不得与 conforming 数据并列排名**。

## 7. 与金标集的接口契约

> 金标集由 C 组「金标集构造」方向产出。抽取器规格与评测器共用下面这个 JSONL schema。

### 7.0 抽取器输入切片（裁决 ⑨-a：**绝不能含答案**）

抽取器能看到的输入**只有三件**：

```json
{
  "id": "psc-001",
  "task": "<任务描述>",
  "initial_frame": "<严格四段式：候选集/封闭性/评估维度/硬约束>",
  "trace": "<多阶段执行记录>"
}
```

**绝不能**包含：
- `frame_note` —— 金标专有（域外参考），**抽取器不可见**
- `gold` / `out_of_frame_directions` / `in_frame_directions` —— 那是答案

闭卷下抽取器要做的**不是**找答案清单，而是语义判断：
「这个动作是不是【候选集】里的常规解」→ **不在候选集里 = 域外**。
只需要知道域内是什么，不需要知道域外是什么。

> 评测器提供 `evaluator.extractor_input(gold_item)` 做这个切片，调用方不要自己拼。

### 7.1 trace 规范（裁决 ①-a：**强烈建议必填**）

trace 的每一项除 `stage` / `content` 外，**强烈建议**携带两个字段：

```
candidates[]  —— 该阶段进入过候选池的所有方向（含后来被淘汰的）
dropped[]     —— 被淘汰的方向 + 淘汰理由（谁否决的、为什么）
```

```json
{"stage": "select",
 "content": "还可以看看家庭支持这个维度，但本题没给这个维度，先划掉。",
 "candidates": ["按分数位次排序", "比较就业率", "把家庭支持作为选校维度"],
 "dropped": [{"direction": "把家庭支持作为选校维度",
              "reason": "本题未给该维度，超出评估维度范围",
              "by": "收敛阶段自检"}]}
```

**为什么这是根本解法**：区分 `selection_failure` 与 `expression_failure` 需要「它有没有活过筛选」
的**正向证据**。只有候选清单与淘汰记录能提供这个证据 —— 光看方向出现过几次是看不出来的。
没有这两个字段，PSC-Eval 对 selection/expression 的判准率**不可信**。

> **跨组接驳提示（对 A 组）**：multi-mind 的 **N2 阶段本来就有候选清单，N3 本来就有攻击/盲点结果**
> —— A 组的 trace 结构**天然满足**这个要求，它已经具备区分 selection 与 expression 所需的信息，
> 只是没被显式化。这是 C 组给 A 组最便宜的一份礼物。
> 只有 N0/N1 阶段的 trace（还没进候选池）不适用，那里的方向若消失，判 `not_generated` 或 `status_ambiguous`。

**措辞规范的适用边界（裁决 ⑦-d）**：金标集为可控性统一了 trace 措辞
（取舍段一律写「保留」/ 带显式否决词）——**该规范仅适用于金标集**。
接真实系统 trace 时，status 判定必须回到**语义判定**（有没有否决痕迹/保留痕迹），
**不得依赖任何特定措辞**。评测器同时实现词法捷径基线并报告其得分，
就是为了让「这把尺子是不是只学到了关键词」变得可见。

### 7.2 `initial_frame` 强制模板（裁决 ④）

```
【候选集】<显式枚举的常规候选；至少列出题面蕴含的全部常规选项>
【封闭性】closed | open
          closed = 该候选集穷尽了本题的全部可能解
          open   = 该候选集只是常规解，题面允许更多
【评估维度】<显式列举用于比较候选项的维度>
【硬约束】<不可违反的边界；没有就写"无">
```

**封闭性声明是本次裁定新增的关键项**：没有它，逃逸测试的「新候选」一类在描述式框架下无从判定。

- `closed` 框架下：引入清单外候选 = 逃逸成功 = 域外
- `open` 框架下：「新候选」一类逃逸**自动失效**，只剩「新维度 / 新约束 / 新问题 / 重定义」四类可判

评测器会检查 `initial_frame` 是否符合本模板；不符合的标 `frame_schema: "non_conforming"`，
**报告中不得与 conforming 数据并列排名**（只能做「同一任务内的相对比较」）。

**一行一条记录（gold）**：

```json
{
  "id": "psc-001",
  "task": "为一名山东考生推荐 5 所大学",
  "initial_frame": "【候选集】985/211 院校中的候选学校\n【封闭性】closed\n【评估维度】分数位次、就业率\n【硬约束】无",
  "trace": [
    {"stage": "explore", "content": "先按分数位次排一下。",
     "candidates": ["按分数位次排序"]},
    {"stage": "select", "content": "另外考虑一下地域因素对就业的影响？……不对，本题不讨论这个维度，先划掉。",
     "candidates": ["按分数位次排序", "把家庭支持作为选校维度"],
     "dropped": [{"direction": "把家庭支持作为选校维度", "reason": "本题未给该维度", "by": "收敛阶段自检"}]},
    {"stage": "synthesize", "content": "最终推荐：……", "candidates": ["按分数位次排序"]}
  ],
  "final_answer": "……",
  "out_of_frame_directions": [
    {
      "direction": "把「就业质量」之外的家庭支持作为选校维度",
      "status": "selection_failure",
      "decision_effect": "option_added",
      "evidence_quote": "另外考虑一下地域因素对就业的影响？",
      "notes": "被选校阶段明确划掉"
    },
    {
      "direction": "考虑强基计划等特殊招生路径",
      "status": "not_generated",
      "decision_effect": "conclusion_flip",
      "evidence_quote": "",
      "expected_source": "task",
      "notes": "关键漏判：trace 全文无任何提及；该方向由题面隐含的招生路径结构推出"
    }
  ],
  "in_frame_directions": [
    {"direction": "按分数位次排序", "status": "realized", "decision_effect": "none",
     "evidence_quote": "先按分数位次排一下。"}
  ]
}
```

| 字段 | 必填 | 评测器如何使用 |
|---|---|---|
| `id` | 是 | 与预测对齐的唯一键 |
| `out_of_frame_directions` | 是 | 金标正例集，参与 P/R/F1 与 status 混淆矩阵 |
| `in_frame_directions` | 否 | 金标「陷阱集」：框架内方向。用于检测抽取器是否把它们错判成域外（over-claiming） |
| `out_of_frame_directions[].status` | 是 | 金标 status，参与混淆矩阵。canonical = `not_generated`；`discovery_failure` 是别名，**双向归一**，金标可继续写别名 |
| `out_of_frame_directions[].evidence_quote` | 否 | 用于核对金标自身是否可核。`not_generated` 条目**必须留空**，依据写进 `notes` |
| `out_of_frame_directions[].decision_effect` | 是 | schema v2 的硬闸门字段。`not_generated` 条目必须是强效果（`conclusion_flip` / `option_added`）——关键漏判 |
| `out_of_frame_directions[].expected_source` | 否 | 裁决 ⑦-b：记录「这个方向本该被想到」的来源 ∈ {`task`, `external`, `gold_author`}。**仅统计，不参与任何匹配/判定**，也不计入可核率分母 |
| `trace[].candidates[]` / `trace[].dropped[]` | 强烈建议 | 裁决 ①-a：区分 selection/expression 的证据来源 |

**预测文件（pred）**：与 gold 同构的 JSONL，`id` 对齐，`directions` 为抽取器输出。评测器也接受把抽取器输出包在 `prediction` / `extraction` / `result` / `output` 下的写法。

**评测器已兼容的 schema 变体**（`evaluator.py` 实现，测试覆盖）：

| 变体 | 处理方式 |
|---|---|
| 方向集嵌在 `gold` 对象里 | 自动提升到顶层 |
| 证据字段叫 `evidence` 而非 `evidence_quote` | 两种都认 |
| status 写 `discovery_failure` | 归一到 `not_generated`（组章程用词 vs 规格用词，同一件事） |
| `trace` 是纯字符串数组 | 认 |
| 最终答案内嵌在 trace 末段（以「最终答案：」开头） | 自动识别，并**从引用语料中排除** |
| 旧字段 `would_change_decision`（bool） | 兼容映射：true→`conclusion_flip`，false→`none`。**金标集须升级到新字段** |
| 旧 status 名 `discovery_failure` | 归一到 canonical `not_generated`（双向）。报告输出**一律用 canonical 名** |

> **最后一条对本规格的规则 3 是硬性的**：若把最终答案算进可引用语料，
> `expression_failure` 会被系统性误判成 `realized`，三分类归因随之失效。

## 7.3 ★ 硬规则：每条 M2 门槛断言都必须有配对的反向测试

> **「断言通过」不等于「断言有效」。**
> 断言可能因为**检查的对象根本不存在**而恒真 —— 于是「通过」是假的。

本项目为此付过代价，两次都是同一类：

| 症状 | 后果 |
|---|---|
| 金标合规审计只遍历「被抽取器匹配上」的方向 | 未被命中的金标方向从未被审过 → 两项 M2 门槛**假通过** |
| `frame_note` 泄漏断言读 `gold.frame_note`，而金标写在顶层 | 断言恒真 → 「信息不丢」**没真正落实** |

**规则**：每条 M2 门槛断言都必须配一条**反向测试** ——
故意构造能让它失败的数据，断言它**确实失败**。
「让它失败」比「让它通过」更能证明断言是有效的。

`evaluator.py` 里的 `M2_GATE_ASSERTIONS` 列出全部断言与各自的反向测试；
self-test 里逐条实现了这些反向用例。

### 7.3.1 ★ 门槛必须与抽取器**同口径**（⑭-e）

> 门槛基准必须用**与抽取器主表 F1 同口径**的基线分数。
> 拿「含 miss detection」口径的基线去卡「不含 miss detection」的抽取器，
> 等于**双重惩罚**（基线在漏判这一维天然是 0，因为它从不产出 `not_generated`），
> 门槛会被悄悄放松。

主表口径 = 分母只含非 `not_generated` 的金标方向（裁决 ②-b）。
`evaluator.py` 的 `--baseline-main-caliber` 接入的就是这一份。

### 7.3.2 ★ 每个打分函数必须自带**口径不变式**（⑯-b）

> **「报出来的数比该数大」是最危险的失败模式** —— 报错会被查，虚高不会被查。
> **数字看起来漂亮时，先查不变式，再谈结论。**

任何打分函数都必须自带口径不变式断言，且断言必须随函数一起被测试覆盖：

```
assert tp + fn == 主表金标方向数     # 分母 = 非 not_generated 的金标方向数
assert fp + 已匹配数 == 预测总数      # FP 口径
```

用错分母的数据必须**触发断言**，而不是算出一个更大的数。

### 7.3.3 ★★ 跨来源的数字比较前，必须先核对**池口径**与 **scorer 身份**（⑳-c / ⑳-d）

本项目在**口径**上栽了三次，每次的表现都是「报出来的数比该数大或小，但**不报错**」：

| 事故 | 表现 | 后果 |
|---|---|---|
| ⑯-b `fp` 逐条覆盖 | 虚高一倍（0.9381 vs 真值 0.5106） | 门槛被反向抬高 |
| ⑰-e 从旧 CSV 转换 | 继承同一个错值 | 污染两个下游 |
| ⑳-a **池口径不一致**（零方向条目未在池层面清空） | 基线被**低估** 0.06（15 个预测进了主表 FP） | 门槛被放松 |

⟹ **硬规则**：
1. 任何**跨来源**的数字比较（不同实现、不同 CSV、不同脚本产出的数），
   必须先核对**池口径**（零方向条目是否在池层面清空）与**scorer 身份**
   （是不是同一套 `score_prediction`），**再比大小**。
2. **池口径不一致时，该基线不得作门槛基准** —— 评测器必须拒绝把
   `pool_caliber` 不一致的基线接进门槛。
3. 门槛比较是**同点比较**（⑳-b）：抽取器必须在**取得门槛基准的同一个匹配阈值**上
   被评分。禁止抽取器在多阈值上取最优再与门槛比。
4. 任何打分函数都必须自带口径不变式断言（§7.3.2），断言随函数一起被测试覆盖。

## 8. 后处理约定

1. **JSON 解析**：用严格 JSON 解析；解析失败时记录一条 parse_error，不要静默丢样本。
2. **Schema 校验**：检查字段类型与枚举值；不合法的 `status` 归入 `invalid` 桶并计数，不参与混淆矩阵。
3. **`id` 回填**：请求未带 `id` 时由调用方注入，保证与 gold 对齐。
4. **去重**：若两条方向相似度极高（字符二元组 Jaccard ≥ 0.8）且 `in_frame` 相同，保留 `decision_effect` 更强（`conclusion_flip` > `option_added` > `ranking_only` > `additive_only` > `none`）、`evidence_quote` 更长的那条。
5. **人工复核抽样（裁决 ⑥-b：强制，不是建议）**：
   - `decision_effect` 为强效果（`conclusion_flip` / `option_added`）的条目：**100% 复核**
   - `status` 判定：**30% 随机抽样复核**
   - 复核由 C 组主会话执行，结果写入 `goldset/README.md` 的复核记录
   - **复核发现的错误必须回改金标，并在报告里记录改了多少条** —— 金标改了却不记录，等于偷偷改了考卷

   理由：这是硬闸门。硬闸门抽错就等于放水；规格里写「建议」，执行时会被省掉，所以改成强制。

6. **canonical 名检查**：报告输出的混淆矩阵、`per_status` 一律用 canonical 名 `not_generated`，
   不得出现 `discovery_failure`。金标集可继续写别名（评测器双向归一）。
